# imsg-bridge/v1

Tailscale/LAN-only WebSocket protocol between `imsg-bridge` (Mac) and `imsg-sync` (Linux).

## Transport

- **WSS** with mutual TLS (mTLS)
- One JSON object per WebSocket text frame (newline optional)
- Sync sends `{"type":"ping"}` every 10 seconds. The bridge replies with `{"type":"pong"}`. Sync reconnects after 30 seconds without inbound traffic.

## Envelope

```json
{"type":"req","id":"1","method":"chats.list","params":{"limit":50}}
{"type":"res","id":"1","ok":true,"result":{"chats":[]}}
{"type":"event","topic":"message","payload":{...}}
{"type":"event","topic":"db.generation","payload":{"generation":"uuid","at":"..."}}
```

## Methods (v1 allowlist)

| Method | Direction | Purpose |
|--------|-----------|---------|
| `status` | req/res | Bridge + imsg readiness |
| `chats.list` | req/res | Paginated chat list |
| `messages.history` | req/res | Per-chat history (`chat_id`, `limit`, `before`) |
| `messages.after` | req/res | ROWID catch-up |
| `messages.search` | req/res | Local search |
| `watch.ack` | req/res | Client ack for backpressure |
| `attachments.fetch` | req/res | Short-lived attachment token |
| `handles.check` | req/res | Handle validation |
| `pair.enroll` | HTTP POST | Pairing enrollment (TLS, no client cert; pairing code required) |

Server pushes `message` events from `imsg watch.subscribe`.

The bridge sends `watch.gap` with a `reason` when its native RPC process restarts, a subscriber misses events, or native `watch.overflow` ends the current `watch.subscribe`. Sync uses `messages.after` with `since_rowid` and `limit` to recover messages, and the bridge resubscribes. It validates the initial `db.generation` greeting before using a saved cursor. A changed generation invalidates cached message IDs and the cursor.

## Local plugin events

The Unix socket sends `sync.message`, `sync.chats`, `sync.link`, and `sync.resync`. A `sync.resync` payload contains `reason` and `chats`. The plugin reloads the open conversation; reason `db_generation` also invalidates its in-memory message cache.

`messages.send` accepts an optional local `client_id`. Sync echoes it in the result and attaches it to the confirmed `sync.message` when the native send result contains an ID. This value correlates UI state. It is not an idempotency key and does not make retries safe from duplicate delivery.

## Pairing (HTTP enrollment)

Separate TLS endpoint on `enroll_port` (default: bridge port + 1). Server-auth only during enrollment.

```http
POST /v1/pair/enroll
{"pairing_code":"abc12345","client_name":"omarchy-laptop","csr_pem":"..."}
```

Response:

```json
{"ca_pem":"...","client_cert_pem":"...","bridge_url":"wss://host:18789/ws","bridge_host":"...","bridge_port":18789}
```

- Pairing codes expire after 15 minutes; `imsg setup` writes a new ticket to disk that enroll reads per request
- Rate limited per source IP
- Linux: `imsg setup pair <code> --host <mac-host>`

## Discovery (optional)

mDNS service `_imsg-bridge._tcp` advertises hostname and ports only — **no pairing code or credentials**. Opt-in via `imsg-bridge init --mdns`. Pairing + mTLS still required to connect.

Tailscale MagicDNS is preferred over mDNS when on a tailnet.

## Security

- Bind to Tailscale/LAN IP only
- mTLS required; unpaired clients rejected
- No raw `imsg` RPC passthrough
- Send methods blocked unless `enable_send: true` in bridge config
